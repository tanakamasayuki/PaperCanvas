# 実機確認

内部の記録。日本語のみ。自動テストで決着できないことだけを扱う。

自動テストの方針とケース一覧は [TEST_PLAN.ja.md](TEST_PLAN.ja.md)。そちらはホスト実行で**紙に出さずに**確かめられることを全部やっている。ここに残るのは、**紙とスキャナが要るもの**だけである。

> **未実施。** 手順だけ先に確定させてある。実施したら §7 に結果を記録する。

## 1. なぜ自動化できないのか

ホストテストが確かめられるのは「生成したビットマップが正しいか」までで、その先には自動化できない変換が 2 つある。

| 変換 | 何が起きるか |
| --- | --- |
| ビットマップ → 紙 | 感熱ヘッドのドットは仕様上の大きさより**滲む**。細い線が太り、白い隙間が埋まる |
| 紙 → 読み取り | スキャナの性能、印字濃度、紙の反射率、角度、距離が絡む |

どちらもプリンターと紙の物性の話で、PaperCanvas の外にある。**だからここで確かめるのは「PaperCanvas が正しいか」ではなく「PaperCanvas のドキュメントが実物に対して正しいか」である。**

具体的には、[GUIDE.ja.md](GUIDE.ja.md) が断定で書いている数字を裏づけるか、書き換える。

## 2. 必要なもの

- 感熱レシートプリンター（58mm、203dpi のもの）。BLE でも シリアルでも
- そのプリンター向けの送信コード（PaperCanvas の外。ESC/POS の `GS v 0` に生バイト列を渡すだけで済むことが多い）
- ラベルプリンター（あれば）
- **バーコードリーダー**。スマートフォンのアプリではなく、できれば業務用のもの
- 定規（0.5mm 目盛りのもの）

## 3. 確認項目

### T1. 印字可能幅（最優先）

[GUIDE.ja.md](GUIDE.ja.md) §1 が「58mm 紙のプリンターはほぼ 384 ドット」と書いている。**手元のプリンターがそうか。**

1. 幅 384 で、左端から右端まで届く 1px の水平線 1 本だけのレシートを刷る
2. 線が紙の端で切れていないか、右にどれだけ余白が残るかを見る
3. 切れていたら実際の値を探す（幅を 8 ずつ減らして繰り返す）

**結果が 384 でなければ GUIDE の表を直す。** ここは利用者が最初に間違える場所で、しかも間違えても何も通知されない。

### T2. フォントサイズの目安

[GUIDE.ja.md](GUIDE.ja.md) §3 の表が「16px ≒ 2mm、まずここから」「12px は小さすぎることが多い」と書いている。**これは机上の計算（203dpi = 8 ドット/mm）で、滲みを見ていない。**

1. `efontJA_16` で同じ日本語の一文を 12 / 16 / 24 / 32px で刷る
2. 腕を伸ばした距離で読めるか
3. 特に**漢字が潰れていないか**（かなは潰れなくても漢字は潰れる）

**表の判断（「12px は小さすぎることが多い」「16px から始めよ」）が実物と合うか。** 合わなければ数字を書き換える。

### T3. ディザをかけた写真

[GUIDE.ja.md](GUIDE.ja.md) §6 が `Bayer4x4` を写真向けとしている。

1. 階調のある写真を 1 枚、`Threshold` / `Bayer4x4` / `Bayer8x8` の 3 通りで刷る
2. 見比べる。**滲みで網目が埋まって真っ黒にならないか**

画面で見た `Bayer8x8` は滑らかだが、感熱では網目が粗いぶん埋まりにくい可能性がある。**画面での評価と紙での評価が逆転するなら、GUIDE の表はその順で書き直す。**

### T4. バーコードが実スキャナで読めるか（最重要）

自動テストは zxing-cpp でデコードしているが、**デコーダは実スキャナより寛容**である。

`examples/ReceiptWithBarcode` を刷って、次を確かめる。

1. **Code 128 が読めるか**（倍率 1、つまり 1 モジュール 1 ドットの状態）
2. **EAN-13 が読めるか**
3. 読めない場合、`moduleWidth` を 2 / 3 と上げて読めるようになる境目を探す

**倍率 1 で読めなければ、GUIDE と README の「収まる最大の整数倍を自動で選ぶ」という既定は危ない。** 「実用上は最低 2 ドット/モジュール」という注意書きが要る。ここは記録しておく価値が高い。

4. クワイエットゾーンを潰した版（`quietZone = false`）を刷って、**読めなくなることを確認する**。ライブラリが既定で余白を確保している理由の裏づけになる

### T5. 帯出力

`examples/StreamBands` の 100 行レシートを実際に刷る。

1. **全行が途切れずに出るか**
2. 帯の継ぎ目に隙間や重なりが無いか
3. 途中で止まらないか（プリンター側のバッファが溢れないか）

ホストテストは「帯を連結すると `build()` と同じバイト列になる」ことを確かめているが、**それを 1 帯ずつ送ったときにプリンターがどう振る舞うかは別の話**である。

### T6. ラベルプリンター

ラベルプリンターがあれば、`examples/HelloLabel` を刷る。

1. 矩形の位置が狙いどおりか
2. **ラベルの縁が切れていないか**（用紙サイズと印字可能領域は別）

## 4. 記録の残し方

各項目について:

- 使ったプリンターの機種名とファームウェア
- 印字濃度の設定
- 刷ったものの写真
- 判定と、**GUIDE / README を直す必要があるか**

**確認していないことを確認したように書かない。** 未実施の項目は未実施と書く。
