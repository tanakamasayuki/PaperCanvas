# 要件

内部の設計記録。日本語のみ。利用者向けの情報は `../README.ja.md`（未作成） と `GUIDE.ja.md`（未作成） にある。

この文書は最初のたたき台（`memo.ja.md`）を書き直したもの。たたき台自体はリリース前に削除するが、git 履歴には残る。たたき台から変えた点とその理由は [DECISIONS.ja.md](DECISIONS.ja.md) §3 にある。

## 1. 何を作るか

PaperCanvas は、レシートおよびラベル向けに、**印刷内容を配置してモノクロ 1bit ビットマップを生成する**ライブラリである。

紙面サイズと描画指示を受け取り、プリンターへ渡せる機種非依存のビットマップを生成することが唯一の責務であり、プリンターとの接続・通信・機種固有コマンドは扱わない。

成果物は 2 つある。

| 成果物 | 内容 |
| --- | --- |
| **Arduino ライブラリ** | `src/`。1bpp ビットマップ生成の本体 |
| **ブラウザツール** | `docs/`。ラベルのレイアウトを組み、**同じ 1bpp 出力をプレビューする**。GitHub Pages で公開。[WEB_TOOL.ja.md](WEB_TOOL.ja.md) |

**両方が揃った時点で 1.0.0 として初回リリースする。途中リリースはしない。**

## 2. 目的

- レシート（固定幅・可変高さ）とラベル（固定キャンバス）を、それぞれに合った利用モデルで扱えるようにする
- プリンター機種・通信方式・バーコード規格から独立させる
- 同じ入力と設定から常に同じビットマップを生成する（決定性）
- 組み込み機器のメモリ制約下で、長尺のレシートでも一定メモリで生成できるようにする
- バーコードなど外部で生成された成果物を、画像として素直に受け入れられるようにする
- ラベルの矩形指定を手書きせずに済むよう、ブラウザツールと共有できるレイアウト定義を持つ

## 3. 対象環境

| 環境 | 位置づけ |
| --- | --- |
| ESP32 系 | 主対象。CI で常時ビルド検査する |
| `lang-ship:host` コア（SDL2） | テスト環境。CI の自動テストはすべてここで動く |
| PSRAM 搭載 ESP32 | 長尺レシート向け。タイルバッファを PSRAM に置ける |
| AVR 系（Uno など） | **対象外**。LovyanGFX が動かない |
| RP2040 / SAMD 系 | LovyanGFX が動けば動くはずだが**検証しない** |

C++ 標準は **C++11** を下限とする。

**依存ライブラリ**

| ライブラリ | 位置づけ |
| --- | --- |
| LovyanGFX | **必須**。描画エンジン。フォント・図形・画像デコードをすべて委譲する |
| LGFXVirtualCanvas | **必須**。タイル分割エンジン。一定メモリでの長尺生成と帯出力を担う |
| BarcodeKit | **任意**。`PaperCanvasBarcode.h` を include したときだけ必要 |

## 4. 対象利用者

- 小型レシートプリンター（感熱・BLE 接続など）へ印字したい開発者
- ラベルプリンターで固定レイアウトのラベルを刷りたい開発者
- 印字内容の組み立てと、プリンターへの送信を分けて設計したい開発者
- LovyanGFX で画面を描いた経験があり、その知識を印刷に持ち込みたい開発者

プリンターのコマンド仕様に詳しくない開発者が主な読者である。エラーメッセージ・設定名・ドキュメントはその前提で書く。

## 5. 責務の範囲

**ライブラリの責務に含む**

- 紙面（キャンバス）のサイズ決定。レシートは内容から高さを確定する
- 描画要素（テキスト・画像・バーコード・罫線・余白）の配置
- 矩形内での寄せ方・スケール・クリップ
- グレースケール中間表現から 1bit へのモノクロ化（閾値／順序ディザ）
- 機種非依存の 1bpp ビットマップ出力、および帯単位のストリーム出力
- 領域外・文字切れ・画像縮小などの診断情報
- ブラウザツールと共有するレイアウト定義（JSON）の**形式定義**

**ライブラリの責務に含まない**

- BLE / シリアル / USB などの接続・探索・再接続・送信
- ESC/POS やメーカー独自コマンドの生成、ビット順や行末パディングの機種別変換
- 印刷ジョブ管理、再送、進捗管理
- バーコード・QR コードのエンコード処理（BarcodeKit または利用者が担う）
- ラベルの完全自動レイアウト、CSS 互換レイアウト、DTP 相当の組版
- GUI 画面向けの部品配置やイベント処理
- フォント資産の同梱（利用者が LovyanGFX の `IFont*` を渡す）
- レイアウト定義 JSON の**パース**（v1.0 では形式定義のみ。§8 参照）

## 6. システム境界

PaperCanvas は印刷システム全体のうち「紙面レイアウトとラスター生成」のみを担当する。

| 段 | 担当 | 例 |
| --- | --- | --- |
| 1 | アプリケーション | 印字内容を用意する |
| 2 | **PaperCanvas** | レイアウトし、1bpp ビットマップを生成する |
| 3 | 機種ドライバ | ESC/POS 等の機種固有データへ変換する |
| 4 | 通信層 | BLE 等でプリンターへ送信する |

段 3・4 を別ライブラリへ置き換えても、PaperCanvas 本体を変更せず使えることを要件とする。

## 7. 対象となる印刷物

### 7.1 レシート

横幅が固定され、内容に応じて縦方向へ伸びる印刷物として扱う。

- 最初に印字可能な横幅（px）を設定する
- テキスト・画像・バーコード・罫線・余白を上から順に追加する
- 各要素の高さを積み上げ、最終的な紙面高さを決定する
- 原則として内容は欠落させず、必要な分だけ縦へ伸ばす
- 自動折り返しは**既定で有効**（縦に伸びるので折り返しても安全なため）

### 7.2 ラベル

幅・高さ・解像度から確定する固定キャンバスとして扱う。自動レイアウトはコア機能としない。

- 各要素は位置と大きさを持つ矩形として定義する
- 矩形内での寄せ方、フィット方法、クリップ方法を指定する
- 自動折り返しは**既定で無効**（固定矩形なので折り返すと溢れるため）
- 矩形指定はラベル専用ブラウザツールで補助する（§8）

## 8. レイアウト定義とブラウザツール

矩形指定を手書きする負担を減らすため、ラベル用のブラウザツールを用意する。**このリポジトリの `docs/` に含め、GitHub Pages で公開する。** 設計は [WEB_TOOL.ja.md](WEB_TOOL.ja.md)。

ツールに求める機能: ラベル幅・高さ・解像度の設定、矩形の追加とドラッグ移動・リサイズ、寄せ方／スケール／フォントの設定、**モノクロプレビュー**、JSON および C++ コード例の生成。

**2 つの成果物の間で共有するのがレイアウト定義 JSON である。** その形式は [LAYOUT_FORMAT.ja.md](LAYOUT_FORMAT.ja.md) で v1.0 に確定させるが、**組み込み側のパーサ実装は v1.1 以降**とする（ツールは JSON と C++ コードの両方を出力するので、v1.0 の利用者は生成された C++ を貼れば足りる）。理由は [DECISIONS.ja.md](DECISIONS.ja.md) D12。

**プレビューの忠実性が最大の技術課題である。** ツールのプレビューが PaperCanvas の出力と一致しなければツールの意味がないが、素直に作るとレイアウト計算とフォント描画が C++ と JS で二重実装になる。出力が 1bpp でアンチエイリアスが無いため完全一致は原理的に到達可能で、達成できたかどうかも 1 ビット単位で検証できる。方針は未確定で、[WEB_TOOL.ja.md](WEB_TOOL.ja.md) §3 に選択肢と論点を記録している。

## 9. 単位

**ピクセルを第一級とする。** API が受け取る座標・サイズはすべて px。

物理寸法から px を求めるヘルパー（`mmToPx(mm, dpi)` など）を `constexpr` で提供するが、API そのものは mm を受け取らない。丸め規則を全 API で定義・テストする負担を避け、結果の予測可能性を最優先する。

## 10. 出力要件

出力はプリンター機種に依存しない共通形式の 1bit ビットマップとする。

| 項目 | 内容 |
| --- | --- |
| 幅 | ピクセル単位のキャンバス幅 |
| 高さ | ピクセル単位のキャンバス高さ。レシートでは内容から確定する |
| 画素データ | 1画素 1bit。**bit = 1 が黒（印字）** |
| ビット順 | **MSB first**。バイトの bit7 が左端の画素 |
| 行情報 | `rowBytes = (width + 7) / 8`。行は必ずバイト境界から始まる |
| 行末パディング | 余りビットは 0（白）で埋める |

この形式は ESC/POS のラスタービットイメージ（`GS v 0`）と同じ並びであり、多くの機種で変換なしに渡せる。ただし**機種別の変換責務は別ライブラリにある**という原則は変えない。

出力方法は 2 つ提供する。

- **全ページ**: 確定サイズの 1bpp バッファを 1 つ返す
- **帯（バンド）**: タイル単位で 1bpp の帯をコールバックへ渡す。ページ全体を保持しない

## 11. モノクロ化

タイルはグレースケール 8bit で描画し、PaperCanvas 側で 1bit へ変換する。

- **閾値**（既定）と**順序ディザ（Bayer）** を提供する
- **誤差拡散は提供しない。** タイル境界をまたぐ誤差の伝播が必要になり、分割数によって出力が変わるため（決定性要件と両立しない。[DECISIONS.ja.md](DECISIONS.ja.md) D4）
- 変換方式は要素単位でも指定できる（ロゴは閾値、写真はディザ）

## 12. 非機能要件

- **決定性**: 同じ入力・同じ設定から常に同じ出力を生成する。**タイル分割数を変えても出力は 1 ビットも変わらない**
- **一定メモリ**: レシートの高さに依らず、必要メモリはタイル予算で決まる
- プリンター機種・通信方式に依存しない
- 異常なサイズ指定、領域外描画、文字切れ、画像縮小を検出して診断として返す
- 動的確保は `build()` / `stream()` の内側に閉じ込め、失敗は失敗として返す（フォールバックしない）

## 13. v1.0.0 の対象範囲

1. レシートの固定幅・可変高さキャンバス
1. レシートへのテキスト・画像・バーコード・罫線・余白の縦積み
1. 同一行に複数の寄せを同居させる行要素（2列「品名 … 金額」／3列「品名 … 数量 … 金額」）
1. ラベルの固定幅・固定高さキャンバス
1. ラベル上の矩形ベースによるテキスト・画像・バーコード配置
1. 画像の寄せ方とスケール（原寸・倍率・領域フィット・縦横比維持）
1. テキストのフォント・サイズ・寄せ方・明示改行・単純折り返し
1. モノクロ化（閾値・Bayer 順序ディザ）と 1bpp ビットマップ出力
1. 帯単位のストリーム出力
1. 診断（領域外・文字切れ・画像縮小）
1. レイアウト定義 JSON の形式定義（パーサは含まない）
1. **ラベル用ブラウザツール**（`docs/`、GitHub Pages 公開、モノクロプレビュー、JSON / C++ 出力）

**途中リリースはしない。上記がすべて揃った時点で 1.0.0 として初回リリースする。**

## 14. v1.0.0 で対象外とするもの

- BLE 接続、サービス探索、再接続、データ送信
- ESC/POS やメーカー独自コマンドの生成
- 印刷ジョブ管理、再送、進捗管理
- バーコード・QR コードのエンコード処理
- 誤差拡散ディザ（§11）
- ラベルの完全自動レイアウト
- 複雑な組版、CSS 互換レイアウト、DTP 機能
- 禁則処理、ルビ、縦書き
- レイアウト定義 JSON の組み込み側パース
- ブラウザツールからプリンターへの直接印刷（Web Bluetooth / Web Serial）
- AVR 対応

## 15. 成功条件

- 利用者がプリンター通信を意識せず、印刷内容から 1bpp ビットマップを生成できる
- レシートは、指定幅に対してテキストと画像を上から順に積み上げられる
- ラベルは、指定矩形とブラウザツールを使って狙った配置を再現できる
- **タイル分割数を変えても出力が完全に一致する**（自動テストで保証する）
- **ブラウザツールのプレビューと実際の出力が一致する**（一致の程度は [WEB_TOOL.ja.md](WEB_TOOL.ja.md) §3 の方針次第。どの方針でも CI のクロス検証で保証する）
- バーコード生成やプリンター通信を別の部品へ置き換えても、PaperCanvas 本体を変更せず使える
- ライブラリの責務が「紙面生成」に留まり、用途拡張によって複雑化しない
