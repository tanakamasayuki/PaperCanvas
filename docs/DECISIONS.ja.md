# 設計決定

内部の記録。日本語のみ。「なぜそうなっているか」の台帳。

決定の内容そのものは [CORE_DESIGN.ja.md](CORE_DESIGN.ja.md) にある。ここには**理由と、採らなかった選択肢**を書く。

## 1. 確定した決定

### D1. 描画エンジンは LovyanGFX を必須依存にする

PaperCanvas は LovyanGFX なしでは動かない。フォント描画・図形描画・座標変換をすべて委譲する。

**理由**: レシートは日本語が前提であり、フォント描画を自前で持つと efont 相当の資産管理・グリフ検索・プロポーショナル幅の扱いを全部抱えることになる。これは「紙面レイアウトに専念する」という中心コンセプトから外れた仕事量で、しかも LovyanGFX がすでに解決している。加えて、テストを `lang-ship:host` コアの SDL2 で回す方針（[TEST_PLAN.ja.md](TEST_PLAN.ja.md)）とも噛み合い、兄弟プロジェクト（LGFXVirtualCanvas / BarcodeKit）と同じ土俵に乗る。

**採らなかった案**:
- *コアは独立、描画はアダプタ*（BarcodeKit と同じ思想）— 依存ゼロは魅力だが、フォント描画をアダプタ任せにすると「同じ入力から同じ出力」の決定性が利用者の環境に依存してしまう。決定性は本ライブラリの中核要件なので譲れない。
- *ハイブリッド（コア独立＋LGFX 標準バックエンド）* — 設計は一番きれいだが層が 1 枚増える。バックエンドが実質 LovyanGFX 1 つしかない段階でその層を作るのは早すぎる。将来必要になったら `MonoPanel` の手前で抽出できる。

**代償**: AVR は対象外になる。レシートプリンターを駆動する機器が AVR である可能性は低く、許容する。

### D2. タイル分割は LGFXVirtualCanvas に委譲する

自前でタイル分割ループを書かず、`LGFXVirtualScreen` を使う。

**理由**: PaperCanvas は要素リストを保持しており、タイルごとに再描画できる。これは LGFXVirtualCanvas のコールバック再実行モデルがまさに想定している使い方であり（SPEC §17「レイアウトライブラリとの関係」）、分割・オフセット隠蔽・クリップ・ダブルバッファ・PSRAM 対応をそのまま享受できる。兄弟プロジェクトなので、必要なら仕様側で調整もできる。

**採らなかった案**:
- *自前のタイルループ* — 依存が 1 つ減るが、分割・クリップ・端数タイル・確保失敗の扱いを再実装することになる。しかもそれは LGFXVirtualCanvas が既にテストで固めた領域で、バグを入れても「分割数によって印字がずれる」という気付きにくい形でしか現れない。
- *分割しない（全ページ 1bpp スプライトへ直描画）* — 384×2000px の 1bpp は 96KB で ESP32 なら載る。だが (a) 中間がグレーにならずディザが効かない、(b) 長尺レシートでメモリが線形に増える、(c) 帯ストリーム出力ができない。3 点とも要件に触れる。

### D3. 出力先は自作 Panel（`Panel_Device` 派生）をシンクにする

`LGFXVirtualScreen` は `LovyanGFX&` のパネルへ転送するモデルなので、PaperCanvas 側で「画面ではないパネル」を用意する。タイルは `grayscale_8bit` で描き、`MonoPanel::writeImage()` が二値化して 1bpp へパックする。

**理由**: これが唯一「LGFXVirtualCanvas を無改造で使いつつ、モノクロ化を PaperCanvas が完全に握る」形になる。グレー中間を挟めるのでディザが効き、帯コールバック出力も自然に出る。`grayscale_8bit` は LovyanGFX の第一級カラーデプス（`lgfx/v1/misc/enum.hpp:463`）で `pixelcopy_t` の変換経路も揃っている。

**採らなかった案**:
- *1bpp の `LGFX_Sprite` をパネル役にする* — 実装は最小で LGFX 内部 API に触れずに済む。だが二値化が LGFX の色変換任せ（実質単純閾値）でディザ指定ができず、全ページ保持が必須になって帯出力ができない。
- *LGFXVirtualCanvas 側に転送先フック（`setTileSink`）を足す* — 両ライブラリが一番きれいになるが、兄弟リポジトリの仕様変更とリリースが先に必要で、PaperCanvas の初期リリースがブロックされる。**将来 `MonoPanel` の保守が重くなったらこの案へ移行する**（そのとき PaperCanvas 側の API は変わらない）。

**検証済み（`tests/monopanel/`、LovyanGFX 1.2.26 / LGFXVirtualCanvas 1.4.0）**。スパイクで次を確認した。

- `MonoPanel` を載せた `LGFX_Device` を `LGFXVirtualScreen` に渡すと、タイルは `grayscale_8bit`（`getColorDepth()` = 4104）で作られる
- `writeImage()` が各タイルについて呼ばれ、`fp_copy` が**描いたグレー値をそのまま**供給する。384px の階調ランプで不一致 0
- タイルはページ全域を過不足なく覆う（`minY=0` / `maxY=199`）
- メモリ上限 5 通り（タイル数 2 / 4 / 4 / 10 / 20）で出力バイト列が完全一致
- 帯出力（200 行）が全ページ出力とバイト単位で一致

**実装上の落とし穴**: `fp_copy` は行を進むごとに `param->src_x32` を進めるので、**行ごとに元の値へ戻さないと**次の行がタイルバッファの先を読み続け、最終的に範囲外に出る。`Panel_FrameBufferBase` が `sx32` を保持し直しているのはこのためで、同じことをする必要がある。タイル高が小さいうちは表に出ず、1 タイルで全ページを描いた時点でクラッシュした。

**退路（不要になったが記録として残す）**: 上記が崩れていた場合は 1bpp スプライトをパネル役にする案へ退避し、ディザを v1.1 送りにする予定だった。公開 API はどちらでも変わらない。

### D4. モノクロ化は閾値と順序ディザ（Bayer）のみ。誤差拡散は採らない

**理由**: 誤差拡散（Floyd-Steinberg 等）は誤差を下方向・右方向へ伝播させるため、**タイル境界をまたぐ近傍依存描画**になる。LGFXVirtualCanvas SPEC §12.1 が明示的に「分割描画と全面描画で一致しない」と警告している類型そのものであり、[REQUIREMENTS.ja.md](REQUIREMENTS.ja.md) §12 の決定性要件と正面から衝突する。

順序ディザはページ絶対座標だけで閾値が決まるので、分割数に依らず必ず同じ結果になる。決定性を保ったまま写真も実用的に印刷できる。

**採らなかった案**:
- *誤差拡散を入れて、タイル間で誤差行を引き継ぐ* — 行分割なら理屈上は可能。だが列分割・並列化・帯の飛ばし読みと両立せず、「分割数を変えても 1 ビットも変わらない」という検証しやすい不変条件を失う。この不変条件はテスト戦略の土台（[TEST_PLAN.ja.md](TEST_PLAN.ja.md) §3）なので手放したくない。
- *閾値のみ* — 実装は最小だが、ロゴ以外の画像がほぼ使い物にならない。Bayer の追加コストは 16 バイトのテーブルと数行なので、割に合う。

### D5. レシートの高さは add 時に逐次確定する

`addText()` / `addImage()` のその場で高さを計算して積み上げる。`build()` で測り直さない。

**理由**: タイル方式では draw がタイルごとに再実行されるため、どちらの案でも**要素は自分のフォント・サイズ・折り返し設定を保持する自己完結レコードでなければならない**。それが決まると、測定を add 時にやるか build 時にやるかは結果が同一になる。同一なら、

- `height()` を `build()` 前でも問える（紙送り量を先に知りたい用途がある）
- パスが 1 本しかないので決定性の説明が簡単
- 測定に必要なのは 1×1 の `LGFX_Sprite`（2 バイト）1 枚だけ

という理由で add 時を選ぶ。

**代償**: 「設定変更は以後に追加する要素にのみ効く」という規則が必要になる。これは仕様として明記し、GUIDE でも触れる。

**採らなかった案**:
- *2 パス（build 時にまとめて測定）* — グローバル設定を後から変えても全体に効く、という一貫性が得られる。だが上記のとおり要素が自己完結レコードである以上その一貫性は元々実現できず、パスが 2 本に増えるだけになる。
- *利用者が最大高を指定する* — 実装は最小だがメモリを無駄にし、溢れたときの扱いを決める必要が出る。

### D6. Receipt と Label は 2 つの具象クラス

`PaperCanvas::Receipt` と `PaperCanvas::Label`。抽象基底も `virtual` も使わず、共通部は非公開の内部エンジンを共有する。

**理由**: 印刷物の種類で利用モデルを分けるのは、たたき台が挙げた設計原則そのものである。レシートは「上から積む」、ラベルは「矩形を置く」で、そもそも同じメソッドを持たない。型で分ければ誤用がコンパイルエラーになる。LGFXVirtualCanvas が `LGFXVirtualScreen` / `LGFXVirtualSprite` を具象 2 本にしたのと同じ判断であり、BarcodeKit の D2（形式ごとに独立クラス）とも揃う。

**採らなかった案**:
- *単一クラス＋モード切替* — 覚える名前は減るが、使えるメソッドがモード依存になり、誤用が実行時エラーになる。
- *Label のみ用意し、レシートはヘルパーで矩形を積む* — コアは 1 つになるが、レシートの「高さが内容で伸びる」性質とラベルの固定キャンバス前提が衝突し、内部が分岐だらけになる。

### D7. 単位はピクセルを第一級とし、mm はヘルパーに留める

**理由**: レシートプリンターの仕様は「印字可能ドット数 384」のように px で与えられることが多く、mm を第一級にすると入口で必ず換算が挟まる。また mm を API 全体で受けると、丸め規則を全 API で定義・テストする必要が生じ、仕様とテストがおよそ倍になる。予測可能性を最優先する本ライブラリでは割に合わない。

`mmToPx(mm, dpi)` を `constexpr` で提供するので、ラベルを物理寸法で考えたい利用者は入口で 1 回換算すればよい。

**採らなかった案**: *px / mm 両対応*（上記の負担）、*mm 第一級*（機器仕様との不一致）。

### D8. フォント資産は同梱せず、`IFont*` を受け取る

**理由**: LovyanGFX が efont 系の日本語フォントを既に持っており、利用者は普段の画面描画で使い慣れている。同梱するとリポジトリサイズとライセンス管理の負担が増える一方、得られるものは「利用者が 1 行書かなくて済む」だけ。

ただし「203dpi のレシートには何 px のフォントが読みやすいか」は利用者が迷う点なので、**選び方を GUIDE に文書化する**。BarcodeKit が倍率と余白の選び方を文書化したのと同じ発想。

### D9. バーコードは 2 経路で受ける

- 任意のバーコードライブラリ → 利用者が `Bitmap` にして `addImage()`。`PaperCanvas.h` だけで動く
- BarcodeKit → `PaperCanvasBarcode.h` を include したときだけ `addBarcode()` が生える

**理由**: たたき台 §8 の「PaperCanvas はバーコードを符号化しない」という責務境界は正しく、そこは変えない。だが倍率の整数化・クワイエットゾーン・ガードバー延長は利用者が必ず自作することになり、間違えると読めないバーコードが刷られる。BarcodeKit が既にその知識を持っているので、任意ヘッダで橋渡しする。`PaperCanvas.h` 本体の依存は増えない。

これは BarcodeKit が `BarcodeKitDraw.h` を別ヘッダにした構図と同じ。

**実装で分かった改良（採用済み）**: 配置ロジックは BarcodeKit の**型を名指しする必要がなかった**。必要なのは `width()` / `height()` / `module()` / `quiet*()` / `barExtends()` という**形**だけで、これは BarcodeKit の API 形状そのものである。そこで配置ロジックを `PaperCanvas/Barcode.h`（BarcodeKit 非依存）に置き、`addBarcode()` をテンプレートメンバにした。結果、

- `PaperCanvas.h` 単体でも BarcodeKit のシンボルを受け取れる（依存は増えない）
- 同じ形を持つ別のエンコーダがそのまま挿さる
- `PaperCanvasBarcode.h` は「BarcodeKit を一緒に include する便宜ヘッダ」になり、**依存を宣言する場所**という役割は残る

利用者から見た D9 の話（「BarcodeKit を使うなら `PaperCanvasBarcode.h`」）は変わらない。

**採らなかった案**:
- *画像として受けるのみ* — 疎結合は最大だが、上記の定型作業を全利用者が書くことになる。
- *`PaperCanvas.h` に統合* — 使い始めは楽だが、バーコードを使わない利用者にも依存を強いる。

### D10. 出力は bit=1 が黒、MSB first、行はバイト境界揃え

`rowBytes = (width + 7) / 8`、余りビットは 0（白）で埋める。

**理由**: この並びは ESC/POS のラスタービットイメージ（`GS v 0`）と同一で、多くの機種で変換なしに渡せる。「1 が黒」は感熱プリンターの直感（1 = 発熱 = 黒）とも合う。機種別変換は別ライブラリの責務という原則は変えないが、既定が最も普及した形と一致していれば、その別ライブラリが薄く済む。

**採らなかった案**: *極性を設定可能にする* — `Bitmap` の意味が設定依存になり、ドキュメントとテストが倍になる（BarcodeKit D4 と同じ判断）。反転が要る機種はドライバ側で反転すればよい。

### D11. 診断は警告ビットフラグ。生成は止めない

領域外・文字切れ・画像縮小は `Warning` のビットフラグに積み、生成は続行する。

**理由**: 1 要素の指定ミスで紙面全体が出ないほうが、実運用では困る。何が起きたかは分かるようにしつつ、紙は出す。動的確保を伴わないので組み込みでも安全。

例外は「倍率 1 でも収まらないバーコード」で、これだけは**描かずに**警告する。読めないバーコードは刷られたほうが有害だから（BarcodeKit の `fits=false` と同じ方針）。

### D12. レイアウト定義は v1.0 では形式のみ定義し、パーサは実装しない

**理由**: JSON スキーマを先に確定させればブラウザツールを先行開発でき、後方互換の縛りも早期に決まる。一方、組み込み側パーサは ArduinoJson 等への依存とテストを持ち込み、初期リリースを重くする。しかもラベルを C++ から直接組む利用者にとっては不要な機能である。

**採らなかった案**: *v1.0 でパーサまで* （初期リリースが重い）、*JSON を完全に後回し* （後から形式を変える痛みが出る）。

### D13. 行内の列配置はライブラリが持つ（グリッド）

「品名は左、金額は右」を利用者が空白でパディングして作ることはできない、という点だけを確定させる。

**理由**:

- プロポーショナルフォントでは空白の幅が揃わず、桁が縦に並ばない
- 等幅フォントでも、必要な空白数を計算するのは利用者の仕事になる（全角・半角混在ならなおさら）
- 入りきらないときの挙動を利用者が毎回書くことになる

行としてライブラリが持てば、幅計算・折り返し・リーダー文字（`合計......¥1100`）を一度だけ正しく実装できる。**右端の列（金額）を絶対に切らない**という規則も型として表現できる。

**複雑さは列数で段が変わる**、という切り分けも確定している。

- **1 列（左／中／右へ寄せる）と 2 列（左右）は簡単。** 基準位置が紙面の端と中心線だけで決まり、列幅を決める必要がない
- **3 列以上はグリッドが要る。** 列幅の配分を決めないと位置が定まらず、行ごとに揺れて表として読めなくなる

**採った形（実装済み、レビュー待ち）— グリッド 1 本。** 列幅（px / % / 残り / 内容ぴったり）と寄せを持つ列定義を宣言し、そこへセルを流し込む。**1 列・2 列の簡易ヘルパーは別実装にせず、暗黙の列定義として同じ経路に載せた。** 実装が 1 本で済み、簡単なケースでも列の概念が破綻しない。仕様は [CORE_DESIGN.ja.md](CORE_DESIGN.ja.md) §4.2.1、検証は `tests/row/`。

グリッドにしたことで副産物がある。**列幅が固定である以上、セルが溢れても他の列は動かない。** たたき台が想定していた「右端の列を絶対に切らない」ための段階的な縮退規則は、構造として不要になった（溢れたセルは自分の列の中で折り返すかクリップされる）。

**採らなかった案**:
- *利用者が空白でパディングする* — 上記のとおり成立しない。
- *タブストップを導入する* — 汎用性は高いが、タブ位置の管理・折り返しとの相互作用・ラベル側での意味づけまで抱えることになり、[REQUIREMENTS.ja.md](REQUIREMENTS.ja.md) §5 の「複雑な組版はしない」から外れる。グリッドなら列が宣言的に決まるので、この問題を持ち込まずに済む。
- *2 列・3 列の固定 API のみ* — 実装は最小だが 4 列以上が入らず、`addRow` の overload が増え続ける。またレシート以外（ラベルの表組み）に転用できない。

### D14. ブラウザツールは同じリポジトリの `docs/` に置き、Pages のブランチ公開を使う

`docs/index.html` にツール本体を置き、GitHub Pages の「Deploy from a branch: main / `docs`」で公開する。**公開用の Action は作らない。**

**理由**: 兄弟 2 つ（[LGFXScreenBuilder](https://github.com/tanakamasayuki/LGFXScreenBuilder) / [phomemo-d30-web-print](https://github.com/tanakamasayuki/phomemo-d30-web-print)）がこの形で、実績がある。esp-flashjs が Action を使っているのは npm ビルド（`web/` → `site/`）を挟むからで、**ビルドレスなら設定 1 箇所で済む**。Arduino ライブラリのリポジトリに Node プロジェクトを併設せずに済むのが大きい。

ツールとライブラリを同じリポジトリに置くのは、両者が [LAYOUT_FORMAT.ja.md](LAYOUT_FORMAT.ja.md) の JSON と**プレビューの一致**という強い結合を持つため。別リポジトリにすると、CI のクロス検証（[WEB_TOOL.ja.md](WEB_TOOL.ja.md) §3.6）がリポジトリ間をまたぐことになり、ずれた瞬間に落とすという仕掛けが成立しにくい。

リリース ZIP からはツール本体を除外する（`tools/release_hooks/pre_release_commit.py`）。設計文書の `.md` は残す。

**採らなかった案**:
- *別リポジトリ* — ライブラリの配布物が軽くなるが、上記のクロス検証が組みにくい。
- *`web/` に置いて Action で Pages へ* — esp-flashjs と同じ形。ビルド工程を持つなら妥当だが、持たないなら Action は純粋な追加負担。
- *`tools/` に置く* — この家の作法では `tools/` はリリーススクリプト置き場（`bump_version.py`）なので衝突する。

### D15. プレビュー忠実性は lgfx-font-tool に委ねる

**Web フォント（TTF / WOFF）は使わない。** ブラウザのラスタライザは LovyanGFX のそれとは別物で、同じ書体を渡してもグリフのビットマップは一致しない。1bpp でアンチエイリアスが無い以上、その差はそのまま出力の差になる。

**代わりに、LovyanGFX が持っているのと同じフォントデータを同じ規則でデコードする。**

**実装は別リポジトリの部品ライブラリに切り出した。[lgfx-font-tool](https://www.npmjs.com/package/lgfx-font-tool) として完成・公開済み**（MIT、依存ゼロ）。同じ問題を LGFXScreenBuilder も抱えていたため。経緯と実物との対応は [FONT_LIBRARY.ja.md](FONT_LIBRARY.ja.md)。

**字形の正しさは、本物の LovyanGFX に対する 1,860 ケースのバイト単位一致で担保されている。** PaperCanvas 側に残る二重実装はレイアウトだけになった。

**決め手**: fontgen（TTF → u8g2）が**ブラウザ内で動く**こと。利用者が作ったフォントをその場でプレビューするには u8g2 の JS デコーダが要り、それが決まると残り 5 形式の追加コストは小さい（u8g2 が一番厄介なため）。

**採らなかった案**:
- *グリフアトラスをホストで焼いてブラウザが貼る* — フォントを増やすたび焼き直しが要る。
- *全フォントを u8g2 へ変換し、JS は u8g2 デコーダだけ持つ* — u8g2 の送り幅が 7bit で頭打ちになり、**75px の DejaVu72 と Font8 が入らない**。
- *ホストで LovyanGFX に描かせて採取し、JS は中間形式だけ読む* — 全形式の再実装を避けられるが、ブラウザで生成した u8g2 のプレビューに C++ の往復が要る。**この採取の仕組み自体は、テストのオラクルとして残す**（[FONT_LIBRARY.ja.md](FONT_LIBRARY.ja.md) §6.1）。
- *各プロジェクトで個別に解く* — 同じ間違いを 3 回することになる。

**確定していること**:

- **完全一致は原理的に到達可能。** 出力が 1bpp でアンチエイリアスが無いため、AA のブレンド差という逃げ場のない誤差源が存在しない。LGFXScreenBuilder が近似で妥協せざるを得なかった条件とはここが違う
- **達成できたかは 1 ビット単位で検証できる。** [TEST_PLAN.ja.md](TEST_PLAN.ja.md) の分割数不変性テストと同じ構造で、同じ道具立てが使える
- **どの方針を選んでもクロス検証テストは置く。** 同じ JSON を C++ と JS の双方に食わせて 1bpp 出力を比較する（[WEB_TOOL.ja.md](WEB_TOOL.ja.md) §3.6）。ツールとライブラリが別々に育ってもずれた瞬間に落ちる
- **フォントメトリクスの真値はホストから吸い出す。** ブラウザ側で TTF から推定しない。LGFXScreenBuilder の `font_introspect` ハーネスと同じ発想で、真値は実際の LovyanGFX が持っている

## 3. たたき台から変えた点

たたき台（`memo.ja.md`、Draft 0.1、2026-08-03）から変更した点と理由。

| 変更 | 内容 | 理由 |
| --- | --- | --- |
| 描画エンジンを確定 | 「LovyanGFX を利用してよい」→ **必須依存** | 曖昧なままではフォント・画像・テスト方法が決まらない。D1 |
| メモリ方式を確定 | 「全体保持と帯生成の優先順位」→ **LGFXVirtualCanvas に委譲し両方提供** | 分割エンジンを自作せずに一定メモリと帯出力の両方が得られる。D2 |
| モノクロ化を確定 | 「閾値やディザを指定可能にするか」→ **閾値と Bayer。誤差拡散は不採用** | 誤差拡散は決定性要件と両立しない。D4 |
| 単位を確定 | 「px 中心か mm も第一級か」→ **px 第一級、mm はヘルパー** | 機器仕様が px で与えられる。丸め規則の増殖を避ける。D7 |
| 折り返しを確定 | 「初期機能に含めるか」→ **含める。レシート既定 ON、ラベル既定 OFF** | 日本語レシートで利用者負担が大きすぎる。印刷物の性質で既定を分ける |
| 診断を確定 | 「警告として返すか」→ **ビットフラグで返し、生成は止めない** | 実運用では紙が出ることが優先。D11 |
| バーコードに橋渡しを追加 | 「画像として受ける」のみ → **画像経路＋任意ヘッダでの BarcodeKit 連携** | 倍率・余白・ガードバーの定型作業を全利用者に書かせない。D9 |
| 出力形式を具体化 | 「極性が明確であること」→ **bit=1 が黒、MSB first、rowBytes 固定** | 曖昧さを残す理由がない。ESC/POS ラスタと一致させる。D10 |
| ラベルツールの範囲を明確化 | 「JSON 等で定義するか」→ **v1.0 は形式定義のみ、パーサは v1.1** | ツール先行開発を可能にしつつ初期リリースを軽く保つ。D12 |
| ツールを同リポジトリに取り込み | 「製品としては分離する」→ **`docs/` に含め Pages で公開** | プレビュー一致のクロス検証をリポジトリ内で回すため。D14 |
| プレビュー忠実性を要件化 | 「モノクロプレビュー」の一言 → **一致を検証可能な要件として立てる** | ツールの存在意義がここに懸かっており、1bpp なら検証できるため。D15 |
| AVR を明示的に対象外に | 記載なし → **対象外** | LovyanGFX 必須の帰結。曖昧にしない |
| 罫線・空白を要素に追加 | 記載なし → `addLine` / `addRule` / `addSpace` | レシートで必ず要る。無いと利用者が画像で代用することになる |
| 行内の列レイアウトを追加 | 記載なし → `addRow`（グリッド） | 空白パディングは成立しないため。D13 |
