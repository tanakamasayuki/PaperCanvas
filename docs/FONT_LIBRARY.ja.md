# フォント描画ライブラリ（別リポジトリ）— 要求仕様

**この文書は PaperCanvas の実装対象ではない。** 別リポジトリで作るライブラリへの要求をまとめたもので、固まったらそちらへ移す。PaperCanvas 側は [WEB_TOOL.ja.md](WEB_TOOL.ja.md) §3 でこれに依存する。

## 1. なぜ別にするか

同じ問題を複数のプロジェクトが抱えている。

| プロジェクト | 抱えている問題 |
| --- | --- |
| [LGFXScreenBuilder](https://github.com/tanakamasayuki/LGFXScreenBuilder) | 画面レイアウトのプレビュー。`tests/manual/font_introspect` でホストからメトリクスを吸い出し、`docs/src/font-metrics.json` に持っているが、**グリフごとの送り幅は無く**、文字位置の厳密一致は未解決 |
| PaperCanvas | ラベル／レシートのプレビュー。1bpp なので**完全一致が到達可能**だが、素直に作るとレイアウトとフォント描画が C++ と JS で二重実装になる |
| 今後のツール | 同じ |

いずれも欲しいものは 1 つ、**「LovyanGFX が描くのと同じ文字を、ブラウザで描く」**である。各プロジェクトで解くと、同じ間違いを 3 回する。

## 2. 何を作るか

**LovyanGFX のフォント描画を JavaScript で再現するライブラリ。**

入力はフォントデータと文字列、出力は 1bpp のビットマップとメトリクス。描画先（Canvas / ImageData / 生バイト列）は利用側が決める。

## 3. 核心 — なぜ「同じバイト列を読む」のが要点か

**Web フォント（TTF / WOFF）を使う案は採らない。**

ブラウザのラスタライザは LovyanGFX のそれとは別物である。同じ書体を渡してもグリフのビットマップは一致しない。ヒンティング、丸め、サブピクセル配置がすべて違う。**1bpp でアンチエイリアスが無い**印刷用途では、その差がそのまま「線が 1 px ずれる」「点が消える」として出る。メトリクスだけ合わせても字形が合わない。

そして LovyanGFX の内蔵フォントはそもそも TTF ではない。

**採るのは「LovyanGFX が持っているのと同じフォントデータを、同じ規則でデコードする」案。** そうすればグリフのビットマップは定義上一致する。近似ではなく同一になる。

### 3.1 対象フォント形式

LovyanGFX 1.2.26 の `lgfx_fonts.hpp` にある形式（実装の系統ごと）。

| 形式 | クラス | 該当フォント | 優先度 |
| --- | --- | --- | --- |
| **u8g2** | `U8g2font` | **efontJA / CN / KR / TW、lgfxJapanGothic / Mincho（P 付き含む）** | **最優先。CJK は全部これ** |
| GFXfont | `GFXfont` | Free* 系、TomThumb、DejaVu、Orbitron、Roboto、Satisfy、Yellowtail | 高。ラテン表示用の主力 |
| BaseFont 系 | `GLCDfont` / `FixedBMPfont` / `BMPfont` / `RLEfont` | Font0 / 2 / 4 / 6 / 7 / 8、AsciiFont8x16 / 24x48 | 中。LGFX 既定フォント |
| BDFfont | `BDFfont` | — | 低 |
| VLW | `VLWfont` | 実行時ロード。アンチエイリアス付き | 低。1bpp 用途では価値が薄い |

**u8g2 だけでレシート／ラベルの用途はほぼ満たせる。** `U8g2font` は生の u8g2 バイト列（`constexpr U8g2font(const uint8_t* u8g2_font)`）を保持しているだけなので、JS 側のデコーダは**同じバイト列を読む**ことになる。

fontgen（LGFXScreenBuilder の `docs/fontgen.html`）が出力するのも u8g2 なので、**利用者が作ったフォントもそのまま同じ経路に乗る**。ここが「全部 u8g2 に寄せる」案の本当の利点で、変換のためではなく**経路を 1 本にするため**である。

### 3.2 フォントデータをどう届けるか

**未確定。** 決めるべきこと。

- LovyanGFX 内蔵フォントのバイト列を、どういう形で配布するか（生成スクリプトでソースから抽出するか、成果物をコミットするか）
- サイズ。efontJA_16 は BMP 全域で数百 KB あり、ブラウザへ丸ごと送るのは重い。**サブセット（使う文字だけ）**か、遅延ロードか
- ライセンス表示（efont、Noto、Adafruit GFX の Free* はそれぞれ条件が違う）

## 4. 機能要求

### 4.1 必須

1. **形式デコーダ** — §3.1 の形式から、コードポイントを与えてグリフのビットマップとメトリクスを取り出す
2. **テキストレイアウト** — `LGFXBase` と同じ規則で送り幅を積む。`textWidth()` / `fontHeight()` 相当を提供する
3. **文字倍率** — `setTextSize()` 相当（整数倍・非整数倍とも LGFX と同じ丸めで）
4. **datum** — `setTextDatum()` 相当の基準位置計算
5. **1bpp 出力** — bit=1 が黒、MSB first（PaperCanvas と同じ並び）。他の出力形式は利用側で変換する

### 4.2 やらないこと

- 描画先の抽象化（Canvas への貼り付けは利用側）
- レイアウト（折り返し、列、矩形配置）— それは各プロジェクトの仕事
- フォント生成（TTF → u8g2）— fontgen は別。ただし**生成物を読めること**は必須
- サーバ通信、フォントの自動取得

## 5. 正しさの担保 — ここが本体

**「LovyanGFX と一致する」は主張ではなく検証項目にする。**

```text
同じフォント・同じ文字列・同じサイズ
  → C++（lang-ship:host コアの LovyanGFX）で描画 → 1bpp
  → JS（このライブラリ）で描画           → 1bpp
  → バイト列が完全一致すること
```

- **このハーネスは本ライブラリのリポジトリに置く。** 各利用プロジェクトが同じ仕掛けを作り直さずに済み、保証を継承できる
- 対象は「全フォント × 代表的な文字集合 × 代表的なサイズ」。CJK は常用漢字から抽出する
- 1bpp なのでアンチエイリアスの誤差が無く、**完全一致が到達可能**。「だいたい合う」で妥協する理由がない

LovyanGFX 側の更新でここが最初に壊れるので、CI で回し続ける。

## 6. 各プロジェクトから見た姿

```text
LovyanGFX ────┬─ C++ 側の描画（実機・ホストテスト）
              │
              └─ フォントデータ（同じバイト列）
                     │
                     ▼
              フォント描画ライブラリ（JS）
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
  LGFXScreenBuilder  PaperCanvas   今後のツール
   （画面プレビュー） （紙面プレビュー）
```

各ツールが持つのは**レイアウト計算だけ**になる。字形は共有ライブラリが出す。

PaperCanvas の場合、残る二重実装はレイアウト（列幅の解決、折り返し位置、矩形配置）だけで、これは [WEB_TOOL.ja.md](WEB_TOOL.ja.md) §3.6 のクロス検証が押さえる。

## 7. 決めるべきこと

| 論点 | 内容 |
| --- | --- |
| リポジトリ名 | `lgfx-fonts-js`？ 命名は兄弟プロジェクトの流儀に合わせる |
| 対応形式の範囲と順序 | u8g2 だけで出すか、GFXfont と BaseFont 系まで含めるか |
| フォントデータの配布形 | §3.2 |
| サブセット化 | ライブラリの機能にするか、利用側の責務にするか |
| 一致検証のハーネス | C++ 側をどう回すか（pytest-embedded を借りるか、Node から直接叩くか） |
| PaperCanvas / LGFXScreenBuilder の移行順 | どちらを先に載せ替えるか |

## 8. PaperCanvas 側への影響

- [WEB_TOOL.ja.md](WEB_TOOL.ja.md) §3 の T1 / T2 / T3 は**この方針に置き換わる**。アトラス吸い出し（T2）は不要になる — アトラスを焼く代わりに、同じフォントデータを読むため
- PaperCanvas の v1.0 は**このライブラリに依存する**。したがってブラウザツールの完成はこちらの完成待ちになる
- ライブラリ本体（C++）はこの話に一切影響されない。既に完成している
